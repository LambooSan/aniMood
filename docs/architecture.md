**ТЕХНИЧЕСКАЯ АРХИТЕКТУРА AniMood**

---

**0. Назначение документа**

Этот документ — техническое дополнение к [`documentation.md`](./documentation.md) и предназначен для разработчиков и авторов модулей парсинга (source modules). Если `documentation.md` отвечает на вопрос «что умеет приложение», то здесь описывается «как именно оно это делает»: из каких компонентов состоит система, как данные проходят путь от нажатия пользователя до кадра видео или страницы манги на экране, и какой контракт должен соблюдать модуль источника, чтобы быть совместимым с ядром.

Терминология и общая модель («клиент-агрегатор», «Parser Engine», «Источники») совпадают с разделом 2 `documentation.md` — этот документ раскрывает её на уровень ниже.

---

**1. Общая схема компонентов**

```
┌───────────────────────────────────────────────────────────────┐
│                        AniMood Client                         │
│                                                                 │
│  ┌───────────────┐   ┌────────────────────────────────────┐   │
│  │  UI/UX Layer   │   │            Core Engines            │   │
│  │ D-Pad / Touch  │◄──┤  Video Player | Reader | Text TTS  │   │
│  │   / Desktop    │   └───────────────┬────────────────────┘   │
│  └───────┬────────┘                   │                        │
│          │                            ▼                        │
│          │                 ┌─────────────────────┐             │
│          │                 │    Parser Engine     │             │
│          │                 │ (JS / Lua / Regex)   │             │
│          │                 │  + Module Loader     │             │
│          │                 └──────────┬──────────┘              │
│          │                            │                         │
│          ▼                            ▼                         │
│  ┌────────────────┐        ┌─────────────────────┐              │
│  │  Local Storage  │◄──────┤   Source Modules     │              │
│  │ (кеш/история/   │       │ (по одному на сайт)  │              │
│  │  закладки/БД)   │       └──────────┬──────────┘              │
│  └───────┬────────┘                   │                         │
│          │                            │ WebView (Cloudflare/DDoS-Guard)
│          ▼                            ▼                         │
│  ┌────────────────┐        (Прямые HTTP/HTTPS запросы)          │
│  │ Tracking Sync   │                  │                         │
│  │Layer(Shikimori, │                  │                         │
│  │AniList,MAL,MDL) │                  │                         │
│  └────────────────┘                  │                         │
└────────────────────────────────────────┼─────────────────────────┘
                                          ▼
                          [ Источники / Web Sites ]
                Видео-хостинги (Anilibria, Kodik…), каталоги чтения
                       (MangaLib, Remanga…) и др.
```

Ключевые слои:

* **UI/UX Layer** — рендер интерфейса и обработка ввода (тач, D-Pad, мышь/клавиатура на десктопе).
* **Core Engines** — независимые от источников движки воспроизведения: видеоплеер, ридер (постраничный просмотр), TTS для озвучки текста ранобэ.
* **Parser Engine** — единая точка входа для всех обращений к внешним сайтам: выбирает нужный Source Module, исполняет его в соответствующей среде (JS/Lua/Regex), нормализует результат.
* **Source Modules** — независимые друг от друга модули-адаптеры под конкретный сайт-источник.
* **Local Storage** — кеш офлайн-контента, история просмотра/чтения, закладки, экспортируемая база данных.
* **Tracking Sync Layer** — синхронизация прогресса с внешними трекерами.

**2. Жизненный цикл запроса (сквозной поток данных)**

Типичный путь запроса — от действия пользователя до отображения контента:

1. **UI-событие.** Пользователь инициирует действие (поиск тайтла, открытие серии/главы, продолжение просмотра).
2. **Маршрутизация в Parser Engine.** Engine определяет, какие Source Modules участвуют в запросе — один (если пользователь уже выбрал источник) либо несколько (при глобальном поиске, см. п. 3.1 `documentation.md`).
3. **Формирование запроса модулем.** Модуль строит HTTP(S)-запрос к сайту-источнику по правилам, зашитым в его коде (эндпоинты, параметры, заголовки).
4. **Прохождение защиты (при необходимости).** Если сайт защищён Cloudflare/DDoS-Guard, Parser Engine делегирует запрос системному WebView, который выполняет JS-проверку страницы и возвращает валидные cookies/токены обратно в сетевой слой модуля.
5. **Разбор ответа.** Модуль парсит HTML/JSON-ответ (через Regex-правила, встроенный JS-парсер или Lua-скрипт) и извлекает нужные сущности: карточки тайтлов, список серий/глав, ссылки на видеопотоки или изображения страниц.
6. **Нормализация.** Результат приводится к единой внутренней структуре данных (см. п. 4), одинаковой независимо от того, какой модуль её вернул — это то, что позволяет Core Engines и UI не знать о специфике конкретного сайта.
7. **Кеш/БД.** Нормализованные данные при необходимости сохраняются в Local Storage (история, закладки, офлайн-кеш).
8. **Рендер.** UI/UX Layer и соответствующий Core Engine (плеер/ридер/TTS) отображают результат пользователю.

Сбой на любом из шагов 3–5 (источник недоступен, сайт изменил разметку) изолируется на уровне конкретного модуля и не приводит к падению остальной системы — см. п. 8.

**3. Интерфейс модуля парсинга (Source Module API)**

Каждый Source Module — это независимый адаптер, реализующий единый контракт, который ожидает Parser Engine. Концептуально контракт состоит из четырёх обязательных операций:

* **`search(query, filters)`** — возвращает список карточек тайтлов (id, название, обложка, тип: видео/манга/текст) по поисковому запросу.
* **`getDetails(titleId)`** — возвращает метаданные тайтла (описание, жанры, статус, список серий/глав).
* **`getEntries(titleId)`** — возвращает список серий (для видео/дорам) или глав (для манги/ранобэ) с их идентификаторами.
* **`resolveEntry(entryId)`** — возвращает исполняемый ресурс конкретной серии/главы: ссылку(и) на видеопоток и аудиодорожки/субтитры — для видео, либо набор изображений страниц — для манги, либо текстовый контент — для ранобэ.

Все четыре метода возвращают данные в единой нормализованной модели:

* **Title** — тайтл (id источника, название, обложка, тип контента, метаданные).
* **Entry** (Episode/Chapter) — единица контента внутри тайтла.
* **Resource** (StreamLink/PageImage/TextBlock) — непосредственно воспроизводимый/читаемый ресурс с указанием качества/формата.

Благодаря этой унификации Core Engines (плеер, ридер, TTS) работают с одной и той же структурой данных вне зависимости от того, какой из 200–250 источников её предоставил.

**Движки исполнения:**

* **Regex-пресеты** — для простых сайтов с предсказуемой, статичной HTML-разметкой; минимальные накладные расходы.
* **JS-движок** — для источников с динамическим контентом, требующих логики (пагинация, вычисляемые токены, нестандартные API).
* **Lua-движок** — альтернатива JS для модулей, портированных из экосистем, использующих Lua как основной язык расширений.

Выбор движка — свойство конкретного модуля, а не глобальная настройка.

**Версионирование и обновление.** Каждый модуль имеет номер версии. При изменении структуры сайта-источника модуль перестаёт корректно парсить ответ (пункт 5 жизненного цикла), что фиксируется как ошибка конкретного модуля; обновлённая версия модуля заменяет старую без изменений в ядре приложения или в других модулях.

**4. Видео- и ридер-пайплайны**

**4.1. Video pipeline**

`resolveEntry()` → список доступных потоков (по качеству: 360p–4K) и аудиодорожек → пользователь/авто-логика выбирает поток → системный или встроенный субтитровый рендерер подключает внешние (.ass/.srt) либо встроенные дорожки субтитров → буферизация и декодирование с использованием аппаратного ускорения (GPU) → вывод кадра с поддержкой жестового управления (яркость/громкость/перемотка) и D-Pad/медиаконтроллеров.

**4.2. Reader pipeline**

`resolveEntry()` → упорядоченный список изображений страниц (манга/манхва) → постраничная подгрузка с кешированием соседних страниц для плавной прокрутки → для ранобэ: текстовый контент передаётся либо напрямую в UI для чтения, либо в Text TTS движок для голосового воспроизведения.

Оба пайплайна используют общий слой Local Storage для сохранения прогресса (последняя просмотренная секунда / последняя прочитанная страница).

---

**5. Офлайн-режим и хранилище**

* **Кеш контента.** Resource-объекты (видеофайлы, изображения страниц) могут быть скачаны через Parser Engine и сохранены локально; при последующем открытии той же Entry Parser Engine сначала проверяет наличие локальной копии и только при её отсутствии обращается к источнику.
* **Локальная БД.** Хранит историю просмотра/чтения, закладки и прогресс синхронизации с трекерами. Структурирована так, чтобы быть полностью экспортируемой/импортируемой (бекап настроек и данных, см. п. 3.3 `documentation.md`).
* **Управление местом.** Кеш страниц манги и скачанные серии — раздельные по объёму данные; для контроля используемого пространства это разделение отражено в настройках хранилища (см. рекомендацию 2 в `documentation.md`).

**6. Трекинг и синхронизация**

Tracking Sync Layer работает поверх Local Storage и независим от Parser Engine:

1. При авторизации в трекере (Shikimori, AniList, MyAnimeList, MyDramaList) приложение получает токен доступа к API соответствующего сервиса.
2. Локальный тайтл (полученный от Source Module) сопоставляется (маппится) с тайтлом во внешней базе трекера — как правило, по названию/внешнему идентификатору.
3. При изменении локального прогресса (просмотрена серия / прочитана глава) событие ставится в очередь на отправку в API трекера.
4. При недоступности сети или сервиса — событие сохраняется локально и досылается при следующей успешной синхронизации; конфликты (например, прогресс изменён на двух устройствах) разрешаются по более позднему изменению (last-write-wins).

Модуль трекинга не зависит от того, какой Source Module предоставил контент — сопоставление идёт по метаданным тайтла, а не по источнику.

---

**7. Сетевой уровень**

* Все запросы Source Modules идут напрямую с устройства пользователя к сайту-источнику по HTTP/HTTPS — без промежуточного сервера AniMood (см. п. 2.1 `documentation.md`).
* Поддерживаются системные Proxy и SOCKS5 — их настройка происходит на уровне ОС/сетевого стека устройства, а не внутри приложения.
* Прямая модель означает: (а) минимальную задержку и максимальную приватность (трафик не проходит через сторонние сервера AniMood), но (б) полную зависимость доступности источника от сетевых ограничений конкретного провайдера пользователя.

---

**8. Обработка ошибок и отказоустойчивость**

* **Изоляция сбоя модуля.** Ошибка одного Source Module (недоступность сайта, изменение разметки, неудачное прохождение Cloudflare/DDoS-Guard) обрабатывается локально в рамках вызова этого модуля и не затрагивает остальные модули или ядро приложения — сквозной поиск (п. 3.1 `documentation.md`) продолжает опрашивать остальные источники.
* **Деградация вместо падения.** При сбое модуля пользователю показывается соответствующий тайтл/каталог как временно недоступный, а не приложение целиком.
* **Восстановление.** Требует обновления конкретного модуля разработчиком/сообществом после изменения структуры сайта-источника; до обновления модуль остаётся в состоянии "не работает" изолированно от остальной системы.

**9. Кросс-платформенные особенности**

| Платформа | Ввод | Особенности рендера |
|---|---|---|
| Android | Touch, жесты | Стандартный мобильный UI |
| Android TV | D-Pad, медиаконтроллеры | Укрупнённые фокусируемые элементы, навигация без указателя |
| AniMood MAX (Desktop: Windows/Linux/macOS) | Мышь + клавиатура | Полноэкранный плеер/ридер, поддержка окна произвольного размера |

Все три реализации UI/UX Layer используют один и тот же Parser Engine и один и тот же набор Source Modules — платформенные различия ограничены слоем ввода/рендера и не затрагивают логику получения контента.
